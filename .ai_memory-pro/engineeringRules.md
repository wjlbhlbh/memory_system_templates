# 工程治理细则 (Engineering Rules)

## 1. 证据与结论
- 所有结论必须基于至少一种真实证据：代码、测试、日志、报错、文档或运行结果。
- 没有证据时，只能给出“假设”或“待确认项”，不能给出确定性结论。
- 不伪造测试结果、日志、命令输出、截图或运行结论。

## 2. 风险分级
- L0：文档修改、样式微调、文案调整、不影响行为的重构、小型辅助函数。可直接执行。
- L1：一般功能开发、普通 bug 修复、非核心模块重构、新增单元测试、小范围接口改动。默认直接执行。
- L2：数据库结构变更、批量数据修改、认证/授权/支付/计费逻辑改动、公共 API 行为变化、构建部署配置变更、重要新依赖、跨模块大改。必须先确认。
- L3：删除重要数据、不可逆迁移、生产环境操作、安全策略变更、可能导致服务中断的基础设施调整。默认不自动执行。

## 3. 需求澄清与意图翻译
- 实施前必须明确：用户原话、真实意图、成功标准、明确非目标、任务分级。
- 用户不懂技术细节是常态，不得因为表达不专业就按字面扩写需求或直接动代码。
- 若存在多个合理解释，默认选择最小、可回退、最不破坏既有行为的一种。
- 只要歧义会影响数据、兼容性、公共行为、权限边界、依赖、部署或架构，就必须先停在方案阶段确认。
- 复杂任务开始前必须写出 Requirement Checklist 草案，把用户要求、边界、非目标、验收命令逐条列出。
- 完成前必须复核 Requirement Checklist，任何未实现或未验证项都必须如实标为未覆盖，不得用“整体完成”掩盖。

## 4. 必须先确认的操作
- 修改数据库 schema、执行迁移、批量导入/更新/删除数据。
- 修改认证、授权、风控、支付、计费相关逻辑。
- 修改公共 API 的输入、输出、状态码、字段语义。
- 删除或重命名关键文件、关键表、核心类、公共函数。
- 引入会影响构建、体积、许可证或运行方式的新依赖。
- 修改 CI/CD、Docker、Nginx、环境变量、密钥加载方式。
- 触发部署、发布、回滚、生产环境命令。
- 大规模重构或任何不可逆操作。

## 5. 编辑与兼容
- Search/Replace 前必须确认上下文仍匹配当前物理文件。
- 禁止为了方便而整文件重写。
- 禁止擅自删除历史记忆、历史日志或用户已有改动。
- 指令优先级：用户明确要求 > 真实环境约束 > 仓库现有约定 > 框架惯例 > 本模板规则 > 个人偏好。
- 修改公共接口时必须识别调用方，优先兼容；若不能兼容，必须明确标记 breaking change。

## 6. 范围保护与回归验证
- 修改前先列出“禁止误伤项”：不应被破坏的模块、页面、接口、数据流、测试口径、部署路径。
- 未验证前不得宣称“只影响这里”或“其他模块不会受影响”。
- 修复 bug 或实现功能时，至少对直接相邻能力做一次回归验证，避免修一处坏一片。
- 遇到跨模块改动时，优先拆成多个可验证阶段，而不是一次性大改。
- 如果任务不能在一次会话内独立验证，必须拆到 `masterTaskLedger.md`；每个子任务应能独立完成、独立验证、独立交接。
- 如果上下文超过单次可控范围，必须创建 `task-packs/*.md`，明确 required reading、do not read、acceptance、handoff。

## 7. 安全底线
- 所有外部输入默认不可信，必须验证、约束、清洗或转义。
- 禁止硬编码密码、密钥、令牌、连接串。
- 禁止在日志和报错中泄露敏感信息。
- 涉及鉴权、权限边界、支付、导出、Webhook、文件上传、管理后台时，默认按高风险处理。

## 8. 源码提交与本地备份分层
- 任务完成并验证后，默认执行：`git status` -> `git add` -> `git commit -m "中文提交名"` -> `git push`。
- 源码、文档、测试、配置的正常修改进入 Git。
- 本地备份统一放入 `.archive/`，并确保 `.archive/` 写入 `.gitignore`。
- 本地数据库、日志、缓存、临时目录、运行产物必须写入 `.gitignore`。
- 若运行产物已经被 Git 跟踪，使用 `git rm --cached` 取消跟踪并保留本地文件。

## 9. 连续开发、并行协作与恢复协议
- `activeContext.md` 是当前执行真相源；进入多轮任务后，状态变化、方案锁定、verified checkpoint、并行分工、交接前都必须更新。
- `progress.md` 只记录已验证事实；长任务按 checkpoint 持续写入，避免上下文压缩后丢失阶段成果。
- `activeContext.md` 与 `progress.md` 属于单写者文件；多 Agent 并行时只允许主 Agent (main agent) 写入，子 Agent 只能回传：目标边界、修改文件、验证结果、未解决风险。
- 多 Agent、长任务、跨模块任务必须使用 `masterTaskLedger.md` 记录状态、locked files、verification evidence 和交接要点。
- 单任务上下文过大时使用 `task-packs/`，且恢复时只读相关任务包，不重读全量历史。
- 长期历史、过期交接和大段日志进入 `history/`，不得让 `activeContext.md`、`progress.md`、`masterTaskLedger.md` 承担归档库职责。
- 禁止子 Agent 直接改主记忆，避免并发写入、状态冲突和覆盖主线恢复锚点。
- 发生 context compression、模型切换、工具切换或人工接管时，先重跑 Fast startup，再按 `activeContext.md` 的恢复必读文件和最近 checkpoint 恢复。
- 恢复时禁止依赖“聊天里大概提过什么”的印象式记忆，必须回到文件化状态。

## 10. 完成门禁 (Definition of Done)
- `[DONE]` 只能用于 Requirement Checklist 全部已实现或已明确非目标，且关键项都有 verification evidence 的任务。
- 缺少真实执行证据时，状态只能是 `[PARTIAL]`、`[AWAITING_QA]`、`[BLOCKED]` 或 `[REWORK]`。
- 用户要求的细节、边界、异常路径、权限边界、兼容性要求必须逐条回应；不能只交付“核心 Demo”。
- 如果某项无法自动化验证，必须写明人工验证步骤、未执行原因和剩余风险。

## 11. 文件编码与完整性
- Agent 可读文件默认使用 UTF-8 无 BOM，尤其是 `.md`、`.json`、`.yaml`、`.yml`、`.txt`、工具入口模板。
- 写文件必须显式指定编码，禁止依赖任何工具、编辑器或系统默认编码。
- 修改记忆文件时，任何工具、命令、编辑器或补丁方式都可以使用，但必须显式保持 UTF-8 无 BOM，不得依赖默认编码或隐式文本输出 (default encoding / implicit text output)。
- 读取失败、乱码、BOM 导致解析异常、JSON 无法解析时，先修复可读性再继续业务改动。
- 修改记忆文件后应检查：关键文件可读、`index.json` 可解析、`startup_order` / `bootstrap_order` 不引用不存在的文件。
