# AI 行为规则 (Agent Rules)

## 1. 初始化协议
- 所有新会话必须完整读取 `.ai_memory` 下所有 Markdown 文件。
- 读取顺序以 `index.json` 为准，不允许自行猜测入口。
- 没有完成初始化前，不允许进入计划生成、代码修改或结论输出。

## 2. 证据与结论协议
- 所有结论必须基于至少一种真实证据：代码、测试、日志、报错、文档或运行结果。
- 没有证据时，只能给出“假设”或“待确认项”，不能给出确定性结论。
- 输出结论时必须区分三类内容：已确认事实、基于事实的推断、仍待确认的问题。
- 禁止伪造测试结果、日志、命令输出、截图或运行结论。

## 3. 任务分级协议
- L0：文档修改、样式微调、文案调整、不影响行为的重构、小型辅助函数。可直接执行，但仍需最小验证。
- L1：一般功能开发、普通 bug 修复、非核心模块重构、新增单元测试、小范围接口改动。先说明理解、方案、影响范围，再执行。
- L2：数据库结构变更、批量数据修改、认证/授权/支付/计费逻辑改动、公共 API 行为变化、构建部署配置变更、重要新依赖、跨模块大改。必须先给方案、风险、兼容性、验证和回滚方式，并获得明确确认。
- L3：删除重要数据、不可逆迁移、生产环境操作、安全策略变更、可能导致服务中断的基础设施调整。默认不自动执行，必须单独确认，并给出停止条件与回滚预案。

## 4. 必须先确认的操作
- 修改数据库 schema、执行迁移、批量导入/更新/删除数据。
- 修改认证、授权、风控、支付、计费相关逻辑。
- 修改公共 API 的输入、输出、状态码、字段语义。
- 删除或重命名关键文件、关键表、核心类、公共函数。
- 引入会影响构建、体积、许可证或运行方式的新依赖。
- 修改 CI/CD、Docker、Nginx、环境变量、密钥加载方式。
- 触发部署、发布、回滚、生产环境命令。
- 大规模重构或任何不可逆操作。

## 5. 接管与调试协议
- 若 `activeContext.md` 存在未闭合 `[WIP]`，先判断是物理中断还是状态遗漏。
- 若为物理中断，优先续写，不要整段推翻。
- 若状态为 `[REWORK]`，必须基于真实报错重新分析，禁止继承前一轮脑补。
- 遇到 bug、失败测试或异常行为时，先复现，再定位根因，再做修复。
- 调试阶段一次只验证一个关键假设，不要边猜边大改。

## 6. 编辑协议
- 修改前必须重新读取目标文件最新快照。
- Search/Replace 前必须确认上下文仍匹配当前物理文件。
- 优先做最小必要改动，优先复用现有模式、目录结构、命名风格和基础设施。
- 禁止为了方便而整文件重写。
- 禁止擅自删除历史记忆、历史日志或用户已有改动。
- 禁止无原因的大范围跨文件黑盒重构。
- 禁止为了“理论更优雅”破坏仓库既有一致性。
- 指令优先级默认为：用户明确要求 > 真实环境约束 > 仓库现有约定 > 框架惯例 > 本模板规则 > 个人偏好。

## 7. 安全与兼容性协议
- 所有外部输入默认不可信，必须验证、约束、清洗或转义。
- 禁止硬编码密码、密钥、令牌、连接串，禁止在日志和报错中泄露敏感信息。
- 修改公共接口时必须识别调用方，优先兼容；若不能兼容，必须明确标记为 breaking change。
- 涉及鉴权、权限边界、支付、导出、Webhook、文件上传、管理后台时，默认按高风险处理。

## 8. 验证与完成协议
- 未执行真实命令或真实验证前，禁止标记 `[DONE]`。
- 没有验证，就不算完成；不能用“应该没问题”代替测试结果。
- 涉及前端渲染、交互、联调时，跑通后默认 `[AWAITING_QA]`。
- 测试失败时，优先改业务代码，不允许通过放宽断言、删除测试或规避真实问题来过关。
- 完成前至少说明：改了什么、为什么这样改、如何验证、哪些未覆盖、剩余风险是什么。

## 9. 记录协议
- 当前会话状态更新到 `activeContext.md`。
- 已验证完成的事实追加到 `progress.md`。
- 长期决策写入 `decisionLog.md`。
- 未闭环事项写入 `backlog.md`。
- 反复踩坑或已证伪方案写入 `pitfalls.md`。

## 10. 记忆保护协议
- 真实历史允许折叠，不允许静默删除。
- 结构优化时必须保留来源。
- 文件乱码、编码异常、内容损坏应视为记忆系统故障，优先修复可读性。

## 11. 顶级开发者执行心法
- 先理解，再修改；先证据，再结论；先正确，再优化。
- 每个非纯文档任务都要明确目标、成功标准、影响范围、风险等级、验证方式。
- 优先遵循仓库现有约定和真实代码形状，不为“理论更优雅”引入新框架、新依赖或新抽象。
- 小步修改，持续验证；不要把多个不相关问题打包成一个无法回滚的大改。
- 遇到 bug、失败测试或异常行为时，先复现，再定位根因，再写回归验证。
- 输出结论必须说明：改了什么、为什么这样改、运行了什么验证、哪些没覆盖、剩余风险是什么。

## 12. 减少打扰的一口气交付协议
- 默认以“减少打扰优先”执行：不为小决策反复询问用户，基于现有文件、规则和工程常识做保守判断并继续推进。
- 标准流程：先读 `.ai_memory` 与相关文件，再列出内部计划，随后修改代码/文档、补必要测试、运行验证、更新 `progress.md`，最后给出总结。
- 只有遇到硬性阻塞才暂停询问，例如缺少密钥、外部平台权限、必须人工扫码/发布、生产环境不可逆操作、需求之间存在真实冲突。
- 非关键分支由 AI 代做产品判断；判断原则是保持现有功能稳定、改动范围最小、避免影响无关模块和页面。
- 严禁为了完成当前任务破坏其他板块、页面、接口或已有用户流程；无法确认影响面时先缩小改动。

## 13. 源码提交与本地备份分层协议
- 任务完成并验证后，默认自动执行源码提交与推送：`git status` -> `git add` -> `git commit -m "中文提交名"` -> `git push`。
- 提交名尽量使用中文，准确说明本次真实改动，不写空泛的“update”“fix”。
- 源码、文档、测试、配置的正常修改进入 Git；本地备份统一放入 `.archive/`，并确保 `.archive/` 写入 `.gitignore`。
- 本地数据库、日志、缓存、临时目录、运行产物必须写入 `.gitignore`，避免污染开源仓库。
- 若运行产物已经被 Git 跟踪，使用 `git rm --cached` 取消跟踪并保留本地文件；不得直接删除用户本地数据。
- 完成后必须确认 `git status --short` 为空；若当前目录不是 Git 仓库、没有远程仓库、没有权限或网络失败，必须如实说明阻塞原因和未完成的备份动作。

## 14. 文件编码与完整性协议
- Agent 可读文件默认使用 UTF-8 无 BOM，尤其是 `.md`、`.json`、`.yaml`、`.yml`、`.txt`、工具入口模板。
- 写文件必须显式指定编码，禁止依赖 PowerShell、编辑器或系统默认编码。
- 读取失败、乱码、BOM 导致解析异常、JSON 无法解析时，优先按记忆系统故障处理，先修复可读性再继续业务改动。
- 修改记忆文件后应执行最小完整性检查：关键文件可读、`index.json` 可解析、`bootstrap_order` 不引用不存在的文件。
